# Dataset Design

A prompt evaluation is only as good as its test set. A clean tool and
a polished judge prompt mean nothing if the inputs are unrepresentative
or the golden answers are wrong. This reference covers how to build a
test set that will actually tell you something.

## The four parts of an eval row

Every eval row, regardless of grading approach, has the same shape:

- **Input** — the variable(s) the prompt template consumes (a question,
  a complaint, an article, a code snippet). Should reflect what real
  users / real callers actually send.
- **Golden answer** — the correct or ideal output. For classification,
  the label(s). For extraction, the expected value(s). For open-ended
  generation, a reference output or a rubric instead of a fixed string.
- **Model output** — what comes out at eval time. You don't write this;
  the eval produces it.
- **Score** — produced by the grader. Pass/fail, a number, or a
  GradingResult dictionary, depending on tool.

Inputs and golden answers are the part you author. Get them right.

## How big should the dataset be?

The course recommends ~100 input/golden-answer pairs for production
evals. For iterating with a human in the loop, **start small (10–30)**.
Small sets are:

- Cheap and fast — the iteration loop stays tight
- Easy to scan by eye when something looks off
- Big enough to expose the obvious failure modes

You grow the set when:

- You find a failure category in production that isn't represented
- You're about to ship a prompt change and want defensible coverage
- You're comparing models and want stddev to mean something

A 12-row dataset that *covers the failure modes you care about* beats
a 200-row dataset of similar easy cases. Diversity > size at small N.

## What to include

A useful 20-case dataset is roughly:

- **~60% typical cases** — the things real users send all day. Boring
  on purpose. These set the baseline.
- **~25% edge cases** — boundary conditions the user already knows
  about. Long inputs, short inputs, multi-label inputs, ambiguous
  phrasing, inputs from underrepresented categories.
- **~15% adversarial cases** — things deliberately designed to break
  the prompt. The fox-leg-counting example from the course is the
  canonical illustration: a math-trick input that exposes weak
  reasoning. For a classifier, an input that genuinely sits between
  two categories. For a refusal-trained prompt, a near-miss request.

The point of the adversarial slice is **not** to drive the pass rate
to 100%. It's to give you a yardstick that doesn't saturate the first
time you fix the easy bugs.

## Sourcing golden answers

Where the golden answer comes from matters as much as having one.

- **Hand-authored by a subject matter expert** — gold standard, but
  expensive. Use for the seed set and for adversarial cases.
- **Hand-authored by the user** — fine for small iteration loops,
  especially when the user *is* the domain expert.
- **Pulled from production logs that were human-reviewed** — great
  when available; you get real distribution for free.
- **Generated by a strong model and then reviewed by a human** — fast
  way to bulk up a set, but the human-review step is non-negotiable.
  Skipping it bakes the bigger model's mistakes into your "ground
  truth".

For open-ended tasks (summarization, explanation, rewriting), a
single fixed golden answer is usually the wrong shape. Switch to a
**rubric** (see `model_graded.md`). Or, if you do keep a reference
output, use it as one possible target, not as exact-match.

## Edge cases worth thinking about

Common categories you should ask about explicitly before declaring a
dataset done:

- **Boundary lengths** — empty input, single token, very long input
- **Format variants** — uppercase, lowercase, missing punctuation,
  multilingual, code-mixed
- **Ambiguity** — inputs that legitimately match more than one
  golden category (decide whether to allow multi-label)
- **Negation and conditionals** — "not a bug, but a feature request"
- **Adversarial near-misses** — for refusal prompts, a benign request
  that pattern-matches a refused one
- **Distribution shift** — inputs from a slightly different domain
  than the user expected (new product line, new locale)

You won't cover all of these in 20 rows. You can cover most of them
in 100. Pick the categories the user's product is most exposed to.

## Storing the dataset

Both approaches in this skill support multiple storage formats.

**CSV** (recommended for promptfoo + structured inputs):

```csv
complaint,golden_answer
"The app crashes when I upload a photo","Software Bug"
"My printer isn't recognized","Hardware Malfunction"
```

**Inline YAML** (recommended for promptfoo + few cases):

```yaml
tests:
  - vars:
      complaint: "The app crashes when I upload a photo"
    assert:
      - type: equals
        value: "Software Bug"
```

**Python list of dicts** (recommended for the Python SDK pattern):

```python
eval_data = [
    {"complaint": "The app crashes when I upload a photo",
     "golden_answer": ["Software Bug"]},
    # ...
]
```

**File-per-case** (recommended when inputs are large, e.g.
articles, transcripts, source code):

```yaml
tests:
  - vars:
      article: file://articles/article1.txt
```

Pick the format the tool consumes most easily, not the one that's
most aesthetic.

## Versioning the dataset

When you ship a prompt change off the back of an eval, **freeze the
dataset version** that scored it. If you keep editing the dataset
during iteration (you will), the v1-vs-v2 prompt comparison becomes
apples-to-oranges. Either:

- commit the dataset alongside the prompt change, or
- tag the dataset (`v0.1`, `v0.2`) when you grow it, and record which
  version produced each score

This is the difference between a regression test and a vibes check.

## When to grow the dataset

Grow it when:

- A real failure shows up that isn't in any current test row → add it
- The pass rate has been 100% for two iterations → either the prompt
  is genuinely good or the set is too easy; add harder cases
- Stddev across runs is so high that the score isn't informative →
  add more rows in the noisy category

Do **not** grow it just because 20 feels small. Grow it because the
current set has stopped being useful as a discriminator.
